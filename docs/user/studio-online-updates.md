# Studio online updates

English | [中文](studio-online-updates.zh.md)

## Versions

Desktop product releases use `apps/desktop/studio-release.json`, starting at `0.1.0`. Electron installer metadata and update comparisons use that version. Harness package manifests keep their upstream version for the bundled runtime. Studio Cloud uses its own `services/studio-cloud/package.json` and lockfile, also starting at `0.1.0`. The two components need not release together. The synchronization protocol remains version 1.

Install the first independent Desktop release manually over an older upstream-numbered installation: the updater will correctly refuse `0.2.1-rc.2` → `0.1.0` as a downgrade. Preserve user data. Later Studio releases compare normally.

## Desktop feed

General Settings includes the installed Studio version and an HTTP(S) update-directory field. Save and restart Desktop to apply a device-local override. Blank means use the packaged source. The existing update control checks metadata, shows download progress, and asks before installation/restart; active work is handled by the existing task-stop confirmation. Ordinary browser clients do not install Desktop packages.

For packaging, set `DSH_STUDIO_UPDATE_URL` to a directory base, for example `https://downloads.example.com/studio/`. Packaging appends `win-x64/`, `mac-x64/`, or `mac-arm64/`. A runtime override is already platform-specific, for example `https://downloads.example.com/studio/win-x64/`. Paths and HTTP intranet origins are supported; embedded credentials, query strings and fragments are rejected.

Upload the installer/archive, blockmap when produced, and the metadata generated by electron-builder into that directory. Keep every referenced filename and SHA-512 unchanged. Stable releases use `DSH_DESKTOP_UPDATE_CHANNEL=latest` and `latest.yml` on Windows or `latest-mac.yml` on macOS. Prerelease builds use `nightly` and its generated metadata. Retain the project's existing signing process; source configuration does not disable signature or checksum verification.

No feed is packaged when the base is blank; Studio does not fall back to upstream release servers or mandatory policy. Publication is an operator action. A source without a published newer release cannot produce a downloadable update.

## Server deployment

The default Compose deployment remains usable without a Docker updater. `/v1/version` reports the installed server version; the admin sidebar and System Updates page display it.

To enable online container replacement, edit the existing deployment's `.env`:

```dotenv
COMPOSE_PROJECT_NAME=studio-cloud
STUDIO_DEPLOYMENT_DIR=/absolute/host/path/to/services/studio-cloud
UPDATE_IMAGE_REPOSITORY=registry.example.com/team/studio-cloud
UPDATE_MANIFEST_URL=
UPDATER_TOKEN=replace-with-at-least-32-random-characters
```

Use the **existing** Compose project name; `studio-cloud` above is an example. Changing it creates a different set of named volumes. `STUDIO_DEPLOYMENT_DIR` must be the real host directory containing `.env`, `compose.yaml`, and `compose.updates.yaml`. Generate the token locally, for example with `node -p "require('node:crypto').randomBytes(32).toString('hex')"`.

Start the opt-in deployment from that directory:

```sh
docker compose -f compose.yaml -f compose.updates.yaml up -d --build
```

The application has no Docker socket. Only the separate updater mounts the socket and deployment directory; enabling it grants that container host Docker control. It exposes no public host port and authenticates the application using `UPDATER_TOKEN`. Keep that token and the existing `MASTER_KEY` intact across updates. For a private registry, mount the appropriate Docker client config into the updater at `/root/.docker:ro`; helper-based credentials also require their helper binary in the updater image. The updater never starts an interactive registry login.

## Server release manifest

Build and publish a server image containing the target `package.json` version. Publish an HTTP(S) JSON file with the following shape, replacing the repository and digest with actual values:

```json
{
  "version": "0.1.1",
  "image": "registry.example.com/team/studio-cloud@sha256:<64 lowercase hex characters>",
  "notes": "Release notes",
  "minimumVersion": "0.1.0",
  "rollbackCompatible": false
}
```

Set this file's address in Admin → System Updates; the address may remain blank until the first release is published. `UPDATE_IMAGE_REPOSITORY` is a deployment allowlist, not editable through release metadata. The image must use its immutable digest. HTTP is supported for intranet sources. The configured release source is trusted to select code; protect it and the registry accordingly.

Check for updates, review the target and release notes, then choose **Back up and update**. The service re-reads the manifest to reject a stale target, creates an encrypted backup through the existing backup policy, and submits a version-bound job. Backup failure prevents dispatch. The updater pulls the exact image, records it in `.env`, and runs Compose for `app` only with `--no-deps --no-build`. PostgreSQL, other services, and named data volumes are preserved. Readiness and `/v1/version` must match before the job completes. The admin page reconnects during service replacement; progress and the backup id persist in `updater-state`.

## Failures and recovery

A pull/preparation failure leaves the running app untouched. A replacement that fails readiness automatically rolls back the **application image only** when `rollbackCompatible: true` explicitly declares database compatibility. It never restores or overwrites the database automatically. Keep that flag false for migrations the preceding image cannot read. In that case a failed replacement requires the administrator to follow the release's migration/recovery instructions using the recorded backup and preserved master key.

An updater restart marks an unfinished job interrupted rather than guessing whether to rerun migrations. Inspect the app image, readiness, and recorded job before retrying. Keep registry access available until the deployment has completed. For offline/manual operation, the existing Compose build and backup/restore commands remain available.

For an external PostgreSQL deployment, set `STUDIO_UPDATE_COMPOSE_FILE=compose.external-pg.yaml` in `.env`, start with `-f compose.external-pg.yaml -f compose.updates.yaml`, and keep the same file for future manual commands. The executor shares `.studio-update/lock` with the existing `scripts/update.sh`; a manual source update and an online image update cannot switch this deployment concurrently. Both use `STUDIO_CLOUD_IMAGE` as the persisted image key.
